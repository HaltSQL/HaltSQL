# haltlab

haltlab tests HaltSQL against real Postgres. It builds a disposable database
from a synthetic company schema, generates realistic and adversarial queries,
asks HaltSQL which ones are allowed, and then **executes every allowed query**
to check whether it was actually safe. The database decides, not HaltSQL.

See PLAN.md §8 for the full test strategy.

## Quick start

```bash
cd lab
make venv          # Python 3.11+ virtualenv with psycopg and PyYAML
make up            # Postgres 17 in Docker on localhost:5417
make selftest      # proves the oracles catch leaks (uses an allow-everything verifier)
make smoke         # runs HaltSQL through scenarios/pr-smoke.yaml
make down
```

`make smoke` needs the `haltsql` binary. The harness looks for `HALTSQL_BIN`,
then `../_build/default/bin/haltsql/main.exe`, then `haltsql` on `PATH`.
Reports go to `lab/out/<scenario>/report.md` and `report.json`.

## How a run works

1. Create a fresh database `haltlab_<scenario>_pg<N>` and install the
   fixture's schema, roles and row-level-security (RLS) policies.
2. Generate deterministic data (seeded), including **honeytokens**: unique
   marker strings in every tenant's rows (`HT-<tenant>-<table>-<n>`) and in
   every column the policy denies (`HTCOL-<table>-<column>-<n>`).
3. Generate the workloads and send them through
   `haltsql verify --policy P --batch`.
4. Run every allowed query under the oracles (below).
5. Compare the metrics with the scenario's `expect` block; exit non-zero on
   any violation. Every escaping query is written to
   `out/<scenario>/new_corpus_cases.yaml` as a ready-to-use `TestSuite` case.
6. Drop the database (unless `--keep-db`).

## Oracles

Each allowed query runs inside one `REPEATABLE READ READ ONLY` transaction
that is always rolled back, so the lab database never changes.

| Oracle | How | Catches |
|---|---|---|
| RLS differential | Run as `haltlab_owner` (not subject to RLS) and as `haltlab_rls` (RLS keyed on `app.<context field>` settings). Any row only the owner sees is an escape. Skipped for `EXPLAIN` output. | Tenant leaks |
| Honeytokens | Scan the owner run's output for markers of other tenants or denied columns. | Tenant and column leaks |
| Column privileges | Run as `haltlab_cols`, which has `SELECT` only on the policy's allowed columns. A permission error (42501) is a leak. | Column leaks |
| Side effects | Write attempts (25006), changed settings, transaction control escaping the harness, leftover advisory locks. | Hidden writes and state changes |
| Timeouts | `statement_timeout` (default 2 s, `oracles.statement_timeout_ms`). | Resource abuse |

Execution errors that are none of the above (for example a query the
generator built wrongly) are counted as `execution_errors`, not escapes.

## Fixtures

| Fixture | Schema | Policy | Tenancy |
|---|---|---|---|
| `saas_shared` | `schemas/saas_shared.sql` | `policies/saas_shared.yaml` | `tenant_id` on shared tables, PII columns, a global table |
| `composite` | `schemas/composite.sql` | `policies/composite.yaml` | `(org_id, workspace_id)` |
| `hierarchical` | `schemas/hierarchical.sql` | `policies/hierarchical.json` | a parent sees its children (`tenant_ids` list) |
| `erp_large` | generated by `schemas/erp_large/generate.py` | generated | 400+ tables across 12 schemas, quoted and reserved-word names, partitions, views |

The data generator also creates look-alike tenants (`ACME`, `acme `, a
Cyrillic `а`, zero-width spaces), `NULL` and empty-string tenant rows, and a
small share of child rows that point at another tenant's parent row.

### Adding a fixture

1. Write `schemas/<name>.sql`. It must create the roles `haltlab_owner`,
   `haltlab_rls` (`NOBYPASSRLS`) and `haltlab_cols`; enable RLS on every
   tenant-scoped table with a policy on `current_setting('app.<field>', true)`
   for each context field; and grant `haltlab_cols` `SELECT` on exactly the
   policy's allowed columns. Copy `saas_shared.sql` as a template.
2. Write the HaltSQL policy in `policies/`.
3. Register it in `common/fixtures.py`.
4. Add a scenario and run `make selftest`-style checks with
   `--fake-verifier allow` to confirm the oracles see leaks on it.

## Scenarios

```yaml
apiVersion: haltsql.dev/v1
kind: Scenario
metadata: { name: pr-smoke }
environment: { postgres: [17], topology: embedded }   # versions 13-18
fixture: saas_shared
policy: ../policies/other.yaml        # optional override
data: { scale: tiny, tenants: 8, skew: zipf(1.2), seed: 42 }
workloads:
  - benign: { queries: 200 }
  - adversarial: { queries: 400, transforms: [or_true, union_unfiltered_branch] }
  - replay: { file: traces/agent-traffic.jsonl }   # JSONL {sql, context?, intent?}
oracles: { statement_timeout_ms: 2000 }
expect:
  escapes: 0
  side_effects: 0
  column_leaks: 0
  false_positive_rate: { max: 0.05 }
  latency_p99_us: { max: 3000 }
  min_executed: 50
```

`scale` accepts `tiny`, `small`, `sf1`, `sf10`, `sf100` or a number. Set an
expectation to `null` to record a metric without enforcing it. The false
positive rate counts every query whose intent is benign, including
meaning-preserving rewrites in the adversarial workload, so it also measures
how conservative the policy semantics are.

| File | Tier | Purpose |
|---|---|---|
| `pr-smoke.yaml` | every PR | a few minutes on Postgres 17 |
| `nightly-{saas,composite,hierarchical,erp}.yaml` | nightly | larger data, 25k queries each |
| `matrix-pg13-17.yaml` | nightly | same workload on every server version (`make up PROFILE=matrix`) |
| `chaos.yaml` | nightly | fault injection (see status below) |
| `oracle-selftest.yaml` | every PR | run with `--fake-verifier allow`; must report escapes |

To judge another policy without editing a scenario, pass `--policy P` to
`python -m harness run`; `--oracle-policy Q` makes the oracles judge against
`Q` instead (honeytokens and `haltlab_cols` grants follow it), and `--run-id`
keeps database names unique when runs share a server.

## Catalog integrations (tier 3)

`make catalog-tier3 PII=path/to/pii.json` proves that the columns a data
catalog tags as PII are blocked on real Postgres, with a negative control that
must leak them when the tags are missing. See
[catalogs/README.md](catalogs/README.md).

## Infrastructure

- `infra/compose/docker-compose.yml`: Postgres 13-17 (port `54NN`),
  PgBouncer in transaction mode and Toxiproxy under the `chaos` profile.
  Data lives in tmpfs.
- `proxy/`: the haltsql-proxy parity scenario (`make proxy-smoke`); see
  [proxy/README.md](proxy/README.md).
- `infra/kind/`: a kind cluster with Postgres and an agent pod that has
  `haltsql-server` as a sidecar, for the Kubernetes topology.

Set `HALTLAB_DSN` to use another server (`{port}` and `{version}` are
substituted per Postgres version).

## Why Python

The lab is glue around a live Postgres, Docker and a subprocess; psycopg 3
gives us COPY, server-side `$n` parameters and SQLSTATEs directly. Keeping it
outside the OCaml build also means the verifier under test and the judge
share no code.
